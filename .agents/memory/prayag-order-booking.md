# Secondary Order Booking source quirks

- One workbook per FY in the Drive folder (config `secondary_order_booking`); NO 2026-27 file exists yet (2025-26 data ends 31-03-2026). When the report-FY file is missing, order columns must grey out with an explicit reason — never silently show zeros. Autodiscovery matches titles containing "2026-27"/"26-27"/"2026".
- Older files (2021-22 → 2023-24): block layout with forward-filled Date/Retailer/TM cells, block-level Sub Total, no Order ID column, serial dates, headers `ID`/`Retailers`/`Team member`. Forward-fill must persist across 50k-row chunk boundaries.
- "Sub Total" is the net measure that reconciles with the workbook's own header total; "Order Value" is gross MRP — use it only as fallback.
- Segment labels are marketing brand lines ("CPVC DURALIFE", "SWR DRAINTECH") but the authoritative INDEX tab keys are item types ("CPVC PIPE"). `config/segment_alias.json` maps brand → INDEX key; INDEX stays the sole authority for the final TYPE. Segments genuinely absent from INDEX (VIGNETTE, MANHOLE COVER, COLUMN PIPE, COCKROACH TRAPS & GRATINGS) stay unmapped and are listed in the Missing Data tab — do not invent mappings.
- **Why** prefix matching is layered: word-boundary prefix ("C P 5000 SERIES" → "C P") plus squashed prefix only for keys ≥4 chars ("PTMTSYMET" → "PTMT") so short keys like "CP" can never claim "CPVC ...".
- Prior-FY files legitimately fail the >95% team-member match target against the current roster (attrition: verified 57/58 unmatched 2025-26 names are truly absent, not normalization misses). Warn below 95% only for the report-FY file; always list unmatched names both directions in Missing Data.
- The management report annual total is re-derived by summing month buckets, so the month helper (`mgmtMonthIndex`) must bucket EVERY parseable date by pure month-of-year (Apr=0..Mar=11) and never drop a row for being "out of the fiscal year". **Why:** an out-of-FY guard silently undercounted the FY25-26 net total by ~₹10.5 Cr; only whole-file inclusion reconciles EXACTLY to the workbook's printed banner grand total (2,310,913,869 = ₹231.09 Cr net). Reconciling to the banner is the proof that net + whole-file are both correct.
- The report is a ROSTER SPINE: only order-booking names that match a roster member are attributed to a member/head. Names that don't match carry real net money the roster can't place (FY25-26: 59 names, ~₹13.59 Cr). Surface this as data-health context (unmatchedNames/unmatchedSale) and a coverage check (attributed share of company total; warn/fail if it drops), NOT a hard failure — roster incompleteness is a data-availability issue, not a code bug.
- "Registered vs Active" members must stay coherent (active ≤ registered): "active" = roster members who booked ≥1 order (matched count, e.g. 141/180 = 78.3%), NOT the distinct-names-in-file count (200, which includes unplaceable names). The file-name count is a separate regression-lock check, labelled as a file statistic, never shown as "active members".
- Verify anchors (`config/verify_anchors.json`) mix ground truth (banner total, order count — externally validated) with regression locks (active counts, per-head net split — pinned to the corrected computation). Cross-foot checks internal consistency (Σ member Sale == Σ head Sale, ±₹1); the remainder to company total is the unmatched money, reported not failed.
