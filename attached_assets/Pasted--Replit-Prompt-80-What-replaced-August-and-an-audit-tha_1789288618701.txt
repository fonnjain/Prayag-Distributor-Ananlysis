## Section B — the audit must not be able to lose a check

```
Code change. Show the diff before applying.

Several audit groups return an EMPTY CHECK LIST when their dependencies
fail. A check that cannot evaluate disappears rather than reporting skip.
That is how the total moved from 49 to 48, and it is why the missing check
cannot now be identified.

1. EXPECTED-KEY MANIFEST

   Every audit group declares the checks it expects to produce. The
   response carries that manifest and compares it against what was
   actually produced.

   Any expected key with no result is reported explicitly as
   not-evaluated, with the reason, and counted. It must never be absent.

2. A GROUP THAT THROWS REPORTS, IT DOES NOT VANISH

   Where an outer error currently returns zero checks, return the group's
   expected keys each marked not-evaluated with the error.

   The audit should be able to say "twelve checks expected, nine ran, three
   could not, here is why" - not silently report nine.

3. THE TOTAL BECOMES MEANINGFUL

   Expected total, evaluated total, and the difference, on every response.
   A shrinking total then explains itself.

4. SNAPSHOT HONESTY

   GET /api/audit serves a snapshot up to 15 minutes old while rebuilding
   in the background. Keep that - it is reasonable - but make it visible:
   the response already carries refreshing and snapshotSavedAt. Surface
   them where a reader sees them, not only in the payload.

   If the snapshot is stale AND a rebuild is running, say so plainly.

DO NOT change any individual check's logic, threshold or outcome. This is
about the audit being able to account for itself.

AFTER APPLYING, print:
  - the expected-key manifest per group
  - a response showing expected, evaluated and not-evaluated totals
  - a forced dependency failure, proving the check reports rather than
    disappears
```

## Notes

- **A4 is the possibility I would test first.** 12,870 is suspiciously close to
  `sale_line` Aug-26 at 12,878, and nowhere near the SKU or order-booking figures.
  If `register_month_state` is shared across tables without a discriminator, the
  baseline may be describing the primary register and the whole August SKU picture
  is being read through the wrong row.
- **Section B is the one that pays off repeatedly.** An audit that can silently
  drop a check is unreliable precisely when it matters — straight after a publish.
  The manifest makes the total self-explaining.
- **Section C item 3 is deliberate.** The instinct on a red check is to make the
  data match it. Here the check is misapplied and the data is correct as it stands.

## What the report got right and is worth recording

**No alert treated August's empty SKU month as zero business.** August is excluded
as unavailable, and only one alert has been raised since 7 September, covering
April–May. The empty-versus-zero discipline held where it mattered most.

**Breadth trajectory and the distributor push list read `sale_line`**, not the SKU
table, so they are unaffected by the August absence. Only retailer-level SKU Deep
Dive and Red Alert B3 depend on it.
