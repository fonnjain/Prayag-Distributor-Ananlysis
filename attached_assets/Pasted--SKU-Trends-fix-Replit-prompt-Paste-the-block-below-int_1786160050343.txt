```
GOAL
Two faults on SKU Deep Dive > Trends. Both make a number on screen mean
something other than what the reader thinks it means.

FAULT 1 - four filters are displayed and none of them do anything.
In artifacts/prayag/src/pages/SkuPage.tsx the trend fetch builds its query as
  new URLSearchParams({ level, scope: "company" })
with a dependency array of [section, level]. The State Head scope dropdown is
ignored, and changing it does not even re-trigger the fetch. Separately the
CompanyReportFilterBar (State Head / State / Distributor) renders whenever
level != "retailer", including on Trends, and entityFilter is never passed to
/api/sku/trend at all. So a salesperson sets his own State Head and reads the
company-wide number believing it is his territory.

FAULT 2 - the same segment shows two different breadth percentages depending
on which tab you are on, and both are labelled "breadth %".
In artifacts/api-server/src/lib/sku/skuFacts.ts:
  getSkuTrend()  calls getEverSoldPerSegment()          <- global denominator
  loadSkuFacts() calls getEverSoldPerSegmentProject()   when level = project
                   or getEverSoldPerSegmentTerritory()  otherwise
The global denominator counts every code ever sold anywhere, including codes
only ever sold to Project / Govt entities. But the Trends NUMERATOR is already
territory-filtered - the query carries the same head_canon != PROJECT_HEAD_CANON
guard the rest of the page uses. So Trends divides a territory numerator by an
all-channel denominator, and every breadth figure on that tab reads
systematically LOWER than the same segment on Overview.

Do PART A first and run CHECKPOINT A before starting PART B. If both parts are
applied before anything is measured, a figure that moves cannot be attributed
to either one.

================================================================================
PART A - THE FILTERS
================================================================================

A1. WIRE THE STATE HEAD SCOPE DROPDOWN
GET /api/sku/trend already accepts scope=head and scopeId. Use them.

  const params = new URLSearchParams(
    scopeHead
      ? { level, scope: "head", scopeId: scopeHead }
      : { level, scope: "company" }
  );

Add scopeHead to the useEffect dependency array so changing it refetches, and
clear trendData in the scopeHead onChange handler the same way the other
sections are cleared.

Do NOT change the snapshot logic in routes/sku.ts. It already serves the cached
snapshot only when scope === "company" && !segment, which is correct - a
head-scoped request must build fresh.

Update the code comment above that dropdown. It currently reads
"applies to Overview / Drill / Timing" and will now apply to Trends too.

A2. HIDE THE FILTERS THAT CANNOT WORK
getSkuTrend does not accept an entityFilter, so State Head / State /
Distributor cannot work on this tab without plumbing that is out of scope here.
Do not plumb it. Hide it.

  {level !== "retailer" && section !== "trends" && (
    <CompanyReportFilterBar ... />
  )}

Check whether Timing has the same problem. If getSkuTiming also ignores
entityFilter, hide it there too. Report what you find either way rather than
assuming.

A3. SAY WHAT THE READER IS LOOKING AT

scope so nobody has to guess:

            : `${levelLabel[level]} - All heads - All FYs`

Also check the amber "Filters active" banner. It fires on
hasEntityFilter(entityFilter). Once the bar is hidden on Trends, a stale
entityFilter left in state from another tab could still fire the banner on a
screen that has no filters - suppress the banner on Trends as well.
```

## Notes for you, not for Replit

**Why the checkpoint matters.** Part A can change what a head-scoped user sees, and Part B changes every breadth figure on the tab. Run separately they are each attributable; run together, a wrong number has two possible causes and you will spend an hour finding out which.

**The one to watch is B-2.** The new breadth figures can only move in one direction - up - because the denominator shrinks. If any segment falls, the agent selected the project denominator for a territory level. The numbers would look entirely plausible and be wrong.

**A-1 is the test that the wiring is real.** If the two figures come back identical, the scopeId never reached the query and the dropdown is still decorative - which is the exact fault being fixed, so an identical pair means nothing changed.

**Still outstanding after this.** State and Distributor filtering on Trends remains unavailable rather than misleading - hidden, not fixed. Plumbing `entityFilter` through `getSkuTrend` (and into the snapshot cache key) is a larger change and worth doing on its own if the business asks for territory-level range trends.
