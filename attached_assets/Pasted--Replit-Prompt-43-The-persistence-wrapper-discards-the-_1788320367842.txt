# Replit Prompt 43 — The persistence wrapper discards the arrears guard

**Date:** 2 September 2026
**Scope:** Section A is read-only and must come back first. Section B is a
one-line code change. Section C is a separate defect, scoping only.

**Standing rule:** every figure states which database or source it came from.

## The defect

The dashboard loader gets August right. Its V4 arrears guard finds 8 of 121
members with August sales — 6.6% against a 15% threshold — and marks the month
unrecorded.

The persistence wrapper then discards that:

```js
const closed = isMonthClosed(monthIdx, fy, now);
const notYetRecorded = !closed && m.notYetRecorded;
```

August is closed, so `!closed` is `false`, so `false && true` is `false`.

**Any arrears month is stored as complete once the calendar passes it**,
regardless of what the guard concluded. Generic, and it recurs at every month
boundary.

## What it is doing right now

**121 members** have August plan above zero and August Order Booked at zero, so
all 121 satisfy the raw A2 condition. **113 open alerts are explicitly labelled
Aug-26.**

Those alerts are not detecting a business problem. They are detecting a sheet
nobody has filled in — and they sit in an engine that escalates to the CEO.

The Secondary Performance page is unaffected. Head labels still read "Apr–Jul",
and eight of ten percentages are unchanged. So the screen is right and the
database is wrong, which is why nobody noticed.

## Section B — the code change, after Section A

```
Code change. One line. Show me the diff before applying.

In the secondary persistence wrapper:

  const notYetRecorded = !closed && m.notYetRecorded;

should be:

  const notYetRecorded = !closed || m.notYetRecorded;

This preserves the loader's arrears decision instead of discarding it on closed
months. An open month stays unrecorded because !closed is true; a closed month
that the V4 guard flagged as arrears stays unrecorded because m.notYetRecorded
is true.

Requirements:

1. Do not change isMonthClosed, the V4 guard, the 15% threshold, or the loader.
   The loader is correct. Only the persistence wrapper is wrong.

2. Do not change the amount-nulling rule that follows it. Once the flag is
   correct, the existing rule nulls plan, ordered and received for unrecorded
   months by itself - which is right, and it is why 152 explicit zeros are

3. Do not touch any frozen year or closed-FY data.

## Section C — a second, separate defect. Scoping only.

```
Read-only. Describe only, change nothing.

isMonthClosed uses:

  return nowMs > Date.UTC(calYear, calMonth + 1, 0);

Date.UTC(year, month+1, 0) is midnight at the START of the month's final calendar
day, not the end of it.

August 2026 therefore became "closed" at 31 August 00:00 UTC - 05:30 IST - with a
full day of the month still to run. The first bad generation was written at
01:17 UTC that morning.

C1. Confirm the off-by-one. Print what isMonthClosed returns for a series of
    timestamps across 30 and 31 August.

C2. Which consumers depend on isMonthClosed? A month closing 24 hours early
    affects anything that treats closure as completeness.

C3. Does the same expression appear elsewhere in the codebase? Print every
    occurrence.

C4. What is the correct expression, and what would change if it were fixed?
    Describe only. Do not apply it - this is a separate change from Section B
    and should not ride along with it.

Report only.

  like a business recovery or a suppression. It is neither, and the reason should

  timing affects more consumers than the arrears flag does.
