## B. The MRP adapter never uses MRP. This is a real defect.

In productWiseMrpAdapter.ts:

```
gross = basicOrderValueExGst / (1 - discountPct/100)
```

MRP is fetched, but it is only used as an include/exclude gate. The gross
is really the CRM's implied gross, rebuilt from the CRM's own discount %,
yet it is labelled "derived from MRP". The label is wrong, and nothing is
checked against the price list.

- **B1.** Compute TWO measures and label each one honestly:

  ```
  gross_mrp     = effective MRP x Qty
                  label: "derived from price list (MRP)"
  discount_mrp  = 1 - basic / gross_mrp

  gross_crm     = basic / (1 - Discount%/100)
                  label: "derived from CRM discount %"
  ```

- **B2.** GST BASIS. Basic Order Value is ex-GST (GST Type = "GST EXTRA",
  18%). Use exactly the same MRP basis convention that primary discount
  uses. State which one it is, and show one worked row from SORD-9 end to
  end.
- **B3.** AGREEMENT CHECK. This is the bridge we never had. For each code:

  ```
  implied_mrp = basic / Qty / (1 - Discount%/100)
  ```

  Compare it with the catalogue MRP. Report the counts of codes within
  1%, within 5%, and outside 5%, with their value. If the typical ratio
  is about 1.18 or about 0.85, that is GST, and you should say so.
- **B4.** UNIT PROBLEMS. In my check, 102 of 2,380 codes have an implied
  MRP that varies by more than 2% within August, for example:

  ```
  120-WS   0.04 to 146      (3,569x)
  127      4.6  to 252
  PW 61    2,070 to 23,115
  PU-13    397  to 4,367
  ```

  These are Qty unit or pack differences, like tanks recorded in litres
  vs pieces. Flag them as UNIT_MISMATCH. Exclude them from gross_mrp and
  count them. Do not price them.
- **B5.** The discount shown on surfaces uses discount_mrp. The CRM
  Discount % is shown alongside as observed. Where the two differ by
  more than 2 points, flag the row.
