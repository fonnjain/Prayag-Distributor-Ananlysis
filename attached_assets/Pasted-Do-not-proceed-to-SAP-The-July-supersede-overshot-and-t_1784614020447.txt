WHAT HAPPENED

  before    5,113 rows / Rs.9.74 Cr
  after     2,628 rows / Rs.4.88 Cr
  sheet     3,175 rows / Rs.6.41 Cr

We were bringing DB DOWN to the sheet. It went BELOW it - DB is now short by
547 rows and Rs.1.53 Cr. The end state should have been DB current == sheet,
because every real billed line exists in the sheet. Falling below the sheet
means value was removed that should not have been.

THE COLOUR MISMATCH IS THE SUSPECT

2,310 of the 2,485 superseded rows had color=NULL in the DB and a colour in the
sheet. Those are pre-colour-capture rows. Their identity key is
(invoice, code, '', qty). The colour-bearing sheet row's key is
(invoice, code, RED, qty). Those are DIFFERENT keys - not an identity match.

So a colourless DB row was superseded as an "orphan" on the assumption its
colour-bearing replacement exists in current. But if that colourless row was
the ONLY copy of a real line - and no colour-bearing equivalent has been
ingested - superseding it removed a real line from the total. That is the most
likely source of the Rs.1.53 Cr overshoot.

THE "SHEET HAS 547 DUPLICATES" CLAIM IS NOT YET PROVEN

The argument that the next sync inserted 0 does not prove the DB is right. It
only proves those 547 sheet rows match SOME current DB row on identity. If two
genuine colour variants in the sheet both map to one colourless DB row, the
sync inserts 0 AND the DB undercounts by one row's value. Same symptom,
opposite meaning. "Inserted 0" cannot distinguish them.

colour handling or deduplication. So compare, for every Jul-26 invoice:
