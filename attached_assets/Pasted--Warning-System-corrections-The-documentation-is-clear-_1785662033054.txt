# Warning System — corrections

*The documentation is clear and the suppression tree is well designed. Six items need changing; the first two are substantive.*

---

```
Prayag app - Warning System corrections. Same global rules. Report each with the
value it produces, not an assertion of success.

1. SALES-LAG MONTHS FIRE SPURIOUS WARNINGS. This is the most serious item.

   A closed month with order booking and ZERO sales received is notYetRecorded -
   a data-entry delay, not performance. The achievement calculation already
   excludes those months from both numerator and denominator.

   Three rules do not know about it:
     A4  (OB - sales) / OB reads 100 per cent -> fires Red
     J2  "booking exists but zero sales received" -> Orange, the same fact again
     TREND  a lag month looks like a collapse, so EVERY other warning on that
            member is bumped one severity level

   So one late entry produces a Red, an Orange, and a level bump across the whole
   card - and the member has done nothing wrong.

   FIX: exclude notYetRecorded months from the trend calculation and from A4.
   Keep J2, but only where the month is genuinely closed AND recorded.
   Report how many members currently carry a lag month and how many warnings
   clear once this is applied.

2. COST THRESHOLDS CONFLICT WITH THE GLOSSARY.
     Warning System I1     Red >10%, Orange >7%, Yellow >4%
     Sales Deep Dive doc   "flagged above ~15%, sector dependent"

   On Anant Singh's mapped active members, I1 fires Yellow for 4 of 8 and Red or
   Orange for none: Prasun 6.0, Shivam 5.7, Ashutosh 5.2, Ankit 4.4 per cent.

   Both documents are live and they describe the same measure differently.
   Decide one set, apply it in both places, and report the firing distribution
   across all mapped members at the chosen thresholds. If most members sit in a
   single band, the bands are not discriminating.

3. PACE USES A GLOBAL ELAPSED FRACTION INSTEAD OF PER-MEMBER ELAPSED MONTHS.
   A2 and C1 divide by "fraction of year elapsed". J3 uses a hardcoded ~65-day

   FIX: use each member's own elapsed months from BD for all pace pro-rating.
   Derive the partial-tenure norm from the team median rather than hardcoding

   b) LEFT MEMBERS. Departed members are excluded from current-period

Acceptance - report each:
```

## What is right and should not change

**The suppression tree.** J1 hiding everything, J3 hiding pace rules, D1 at Red hiding G1/C3/E2 — that is the correct treatment. A root cause should hide its symptoms, and this one is well chosen.

**Trend as a severity modifier rather than its own warning.** Bumping a level on a worsening trend, and lowering one on improvement so a Yellow can disappear, is a better design than a separate trend alert nobody would action.

**The J family framed as "can't judge fairly" rather than performance.** That distinction is what stops an unmeasurable member looking healthier than a measured one.

**J4 is now empty** — all six spelling splits including Pawan are merged, which confirms that work landed.
