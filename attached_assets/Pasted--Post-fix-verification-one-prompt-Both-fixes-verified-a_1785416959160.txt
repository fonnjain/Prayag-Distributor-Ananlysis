## 1. Before the next scheduled sync runs — the serial key migration

`identityKey()` now appends `|sn:N`. Every row already in the database was written under the **old five-field key**.

If `versionedSyncLines` builds its `currentMap` from DB rows that do not carry `serialNo`, then on the next sync **every incoming key will differ from every stored key**, every row will look new, and the sync will tombstone and reinsert the entire fiscal year in one pass.

You caught exactly this for `tombstoneOrphans` — the SELECT was missing `serialNo` and you noted it would have been "100% blast radius". Confirm the same hole does not exist in the hot sync path.

```
Confirm sale_line_all stores serialNo, and that it is populated for existing
FY2026-27 rows rather than null. Report the count of current FY2026-27 rows with
serialNo null.

If any are null, the new key cannot match them and the next sync will supersede
and reinsert everything. Backfill serialNo before the next scheduled run, or gate
the new key behind a check that the stored value exists.
```
