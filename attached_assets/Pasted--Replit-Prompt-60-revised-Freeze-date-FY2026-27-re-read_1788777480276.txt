# Replit Prompt 60 (revised) — Freeze date, FY2026-27 re-read, and weekly three-month re-sync

**Date:** 5 September 2026
**Supersedes:** the earlier Prompt 60.
**Scope:** Section A is a code change. Sections B, C and D are read-only.

**Standing rule:** every figure states which database or source it came from.

---

## The requirement, and what it costs

**Wanted:** re-read the current month plus the three prior months, once a week.
Today that is Jun, Jul, Aug and Sep.

**A frozen month rejects writes.** So re-syncing three prior months requires those
months to be unfrozen. The freeze moves from about 15 days after month end to
about **92 days**.

| | Month-end to freeze | Months open at once |
|---|---:|---:|
| 7th rule (current) | ~7 days | 1–2 |
| **15th rule (Section A)** | **~15 days** | **1–2** |
| Current + 3 prior | **~92 days** | **4** |

And **June and July are frozen right now.** The new rule brings them back into
scope, which means unfreezing two closed months — something this system has never
done.

Section A takes the 15th, which is a small safe improvement and buys nine days on
August. Sections C and D scope the weekly re-sync without building it.

## Section A — freeze at IST midnight on the 15th. Code change.

```
Code change. One function, one constant. Show the diff before applying.

monthFreezeAt in lib/registers/monthlyReplace.ts currently returns:

  new Date(Date.UTC(mon === 11 ? year + 1 : year, (mon + 1) % 12, 7))

That is 00:00 UTC on the 7th = 05:30 IST. Both the day and the time of day
are wrong for an Indian operation.

Change it to IST MIDNIGHT ON THE 15TH of the following month, which is 18:30
UTC on the 14th.

Make the intent explicit in code - a named constant and a comment stating

not leave a bare arithmetic offset; that is what gets "simplified" later by
someone who does not know why it is there.
```

## Section D — the weekly mechanism itself

```
Read-only and scoping only. Build nothing.

D1. What runs the re-sync today, and how would a weekly schedule be added -
    cron, interval, or triggered?

    Note the MRP refresh turned out to be restart-driven rather than
    schedule-driven, firing 18 times in 10 days on deployments. Confirm this
    would not behave the same way.

D2. Each weekly run re-reads roughly 45,000-50,000 primary rows plus the
    secondary sources. What does that cost in time and Drive API quota, and
    does it risk rate limits? Note the Sheets metadata 403s already seen on
    the closed-year workbooks.

D3. REPLACE OR MERGE - THIS IS THE ONE THAT COULD BITE.

    If a re-read finds FEWER rows than the database holds - the 56-row case -
    does the sync adopt the source and delete, or keep both?

    SHORT_READ_TOLERANCE at 0.98 aborts a shrink beyond 2%. A 56-row shrink
    is 0.04% and would pass silently. Under a weekly overwrite those rows
    would simply disappear, with no drift alert, because adopting the source
    IS the design.

    Is that intended? It should be a conscious decision, not a side effect.

D4. What is recorded per run - rows added, removed, changed, per month? A
    weekly overwrite with no ledger makes "when did this figure change"
    unanswerable later.

D5. Do dashboard snapshots, alert history and AI artefacts invalidate when a
    prior month changes? Recomputing August in November moves figures that
    reports have already quoted.

D6. THE TRADE-OFF, HONESTLY. Four fiscal months open at once, anchors
    settling ~92 days after month end, previously frozen months mutable.

    Against: Prayag edit for about two months, so a three-month window
    captures essentially all of it, and the 56-row drift resolves itself.

D7. Is there a middle option? For example weekly re-sync of the current month
    and ONE prior month automatically, with months two and three re-syncable
    only through an explicit, logged operation.

    That catches most edits automatically and keeps older months settled
    unless someone decides otherwise.

D8. Recommend one. Do not implement it.

Report only.
```

## Notes

- **A3 and C4 are the two checks I would not skip.** Both are about a closed month
  reopening. April through July froze months ago; nothing in this change should
  make them writable again without a deliberate decision.
- **C4's safer alternative is worth pressing for.** Applying the new rule only from
  August forward gives the behaviour going forward without touching two closed
  months. If it works, it is strictly better.
- **D3 is the quiet one.** A 56-row shrink is 0.04% and sails past the 2%
  tolerance. Under a weekly overwrite those rows vanish with no alert, because
  adopting the source is the point. That has to be chosen, not inherited.
- **D7 is the option I would look at hardest.** Automatic for the current month and
  one prior, explicit and logged beyond that. Most edits caught, control retained,
  exceptions recorded.
