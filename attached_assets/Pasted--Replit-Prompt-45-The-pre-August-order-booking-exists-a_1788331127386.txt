# Replit Prompt 45 — The pre-August order booking exists and is never stored

**Date:** 2 September 2026
**Scope:** Read-only and scoping only. Write nothing, build nothing, load nothing.

**Standing rule:** every figure states which database or source it came from.

## What I got wrong, and what is actually true

I have said several times that pre-August 2026 secondary order booking has no
usable source. That was wrong, and the code shows it.

The five **Secondary Order Booking Segment Wise** workbooks — FY2021-22 through
FY2025-26 — are configured, readable, and **read every day**. `loadOrderFile`
parses, per row:

```
date, retailerId, retailerName, orderId, teamMember, distributor, segment, state
```

with forward-fill for multi-line orders. `TmOrderAgg` then retains `orderIds`,
`retailers` with amount and order IDs, `distributors`, `perSegment`, `partyState`,
`perStatePerParty`, and `monthAmount[12]`.

FY2025-26 alone reads **379,441 rows totalling ₹2,31,09,13,869**, reconciling
exactly to the workbook's own header total.

**And none of it is persisted.** The only `INSERT INTO` statements for any order
table are `secondary_order_line` and `secondary_order_upload`, and only the
Product-Wise loader writes them. `ingestOrderBookingFy` sounded like the
counterpart but lives in `primarySheets.ts` and mirrors **primary** booking into
`primary_order_line`. There is no secondary equivalent.

The data is read, aggregated in memory behind a TTL cache, served to management
reports, and discarded.

## Notes

- C1 is the central question. `secondary_sku_line` already holds two eras from
  two CRMs distinguished by a `source` column — `pscode3_xlsx` and
  `productwise_xlsx`. If the same pattern works for order booking, this is a
  known shape rather than a new design.
- B3 is a design question and should be answered as one. A year with no product
  code cannot show item lines, and pretending otherwise would be worse than
  showing order-level rows and saying so.
- D3 is the long shot worth taking. PSCode 3 carries an Order ID. If that is the
  same order reference the Segment Wise files use, April to July might be
  reconstructable at order level even without booking-specific columns.
- Nothing here should be built off the back of the reply. The point is to size it.

## What I had wrong

I told you repeatedly that pre-August order booking had no usable source and
that past years would need a million-row migration. Both overstated it. The
parser exists, runs daily, and extracts order IDs, retailers, distributors,
dates, states and segments. What is missing is a writer and a decision about
presenting a period with no order status or item detail.

That is a real piece of work, but a much smaller one than I described.
