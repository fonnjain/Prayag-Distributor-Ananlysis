## Part 2 — The proposed key reintroduces the bug it replaces

```
Prayag app - before building #74, resolve a design contradiction.

Serial number was ADDED to the identity key on 30 July precisely BECAUSE rows
without it collided. From that session, invoice 72600078 carries two WT-4LC-07
PINK lines that are identical on invoice, code, colour, qty AND amount - serials
2506 and 2532. Only the serial separates them.

The proposed key is invoice | code | colour | qty | month + occurrence index,
dropping serial. That works ONLY if the duplicate rows appear in a stable order.
If the sheet re-sorts - which is the very fault being fixed - occurrence 1 and
occurrence 2 swap, and the churn returns under a different name.

The underlying problem is not which field sits in the key. It is that the sheet
contains genuinely indistinguishable rows and has no stable identifier, so ANY
positional tiebreaker is hostage to sort order.

ANSWER THESE BEFORE BUILDING:

1. How is the occurrence index derived?
   If it is assigned by row order as read, it has exactly the same weakness as
   serial. If it is assigned by sorting the duplicate group deterministically -
   invoice date, then amount, then a stable hash of the row's own values - then
   it survives a re-sort. Make that explicit in the design; the distinction is
   the whole fix.

2. How many rows actually need a tiebreaker?
   Measured on the sheet: 31 of 11,812 May rows and 25 of 12,868 June rows share
   all five fields - under 0.3 per cent. If the figure is that small, matching on
   the five fields alone and accepting ambiguity for those rows may be safer than
   any positional scheme. Report the count for July.

   You propose a normal tombstone pass retires them. Confirm the blast-radius

DO NOT clear and re-ingest again. That was done on 30 July and the problem
returned within 48 hours. Fix the mechanism, then let the tombstone pass work.
```
