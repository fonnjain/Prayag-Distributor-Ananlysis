# Replit Prompt 48 — Build FY2026-27 order booking, both eras

**Date:** 2 September 2026
**Scope:** Implementation. Section A is design sign-off before any code.

**Standing rule:** every figure states which database or source it came from.

## What Prompt 47 established

**The sources reconcile exactly.** The PSCode 3 archives match production
`secondary_sku_line` at **₹0 difference** across all four months — 123,326 rows,
₹81,36,40,008 to the rupee. The booking parser and the SKU population start from
identical accepted source lines.

**Every row carries an explicit SORD.** Zero forward-fill needed across all
123,326 rows. The per-member exports repeat the reference on every line.

**No collisions today.** 17,951 distinct Apr–Jul SORDs, zero overlap with August,
zero with FY2025-26.

**But the counter reset.** August runs SORD-9 to SORD-1381 at ~72 orders/day. The
collision horizon is the FY2025-26 minimum, **SORD-21452** — reached in roughly
**280 days, around mid-2027**. Not urgent, but dated, and far cheaper to solve now
while the table is empty than to retrofit later.

**Do both eras together.** C5 puts it at 3–5 days combined. Staging costs an extra
half to one and a half days *and* leaves the page built on Product-Wise-only
assumptions that then have to be reopened.

## Notes

- The ₹0 reconciliation in the controls is the strongest check available. Both
  populations come from the same accepted source lines, so any difference means
  the booking parse diverges from the SKU parse — and that must be found before
  loading, not after.
- A1 is worth doing now rather than later. The collision is nine months out, but
  the table is empty today and retrofitting an identity column into a populated
  table is a different job entirely.
- A4 is the design question with the most user impact. A filter that silently
  drops four months returns a result that looks correct, which is worse than a
  blank page.

## Not in scope

Section D of Prompt 47 — backfilling SORD into `secondary_sku_line` — is not
included. It touches frozen rows for provenance only and does not populate the
page. Not worth the exception.

The five historical Segment Wise years remain a separate decision. FY2021-22 and
FY2022-23 have no Order ID at all, which is a harder identity problem than
anything here.
