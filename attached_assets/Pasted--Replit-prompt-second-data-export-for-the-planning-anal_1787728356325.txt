4. **Preserve raw source shape.** For any spreadsheet source, export the raw cell values with the original header row(s) intact. Do not normalise, rename, or re-map columns during export.
5. **Populate every column you emit.** In the last export, `stock_snapshots.quantity` was `NULL` for all 9,223 rows and the real values were only recoverable from `raw_json`. If a column exists in the CSV, fill it.
6. **If something does not exist, say so.** Do not emit an empty CSV with headers and leave me to infer. Add an explicit line to the README: *"X was requested and does not exist because Y."* That answer is genuinely useful.

## P1 — Blocking

### 1.1 Real plan history, monthly, per segment

The last export contained 86 plan runs, of which 82 carried a test note (`suite-NC9`, `debug-test`, `type-fix-test`, `final-verify`, `Item-6 smoke test`). Only three were finalized, and the only finalized PTMT plan was a smoke test. As a result **planned-vs-produced cannot be compared for any historic month**.

Please export, from production:

- `plan_runs`, `plan_run_results`, `plan_run_inputs`, `plan_run_input_snapshots` — **all rows, all months, both segments**, with `status` and `note` preserved.
- Add a boolean column `is_production_run` distinguishing real planning activity from test/QA traffic, using whatever marker the production system actually uses. If no such marker exists, say so.
- `corrective_plan_runs` and `corrective_plan_items` — all months.
- `plant_month_snapshots` — all months, with `payload_json` intact.

**If production has no plan history before July 2026**, then instead export the *source planning workbooks* Prayag used before the app existed — the Google Sheets or Excel files that held the monthly Max/Min production plan per item. One tab per month is fine. State clearly which months exist and which do not.

Anchor to include: for each month and segment, the plan grand total (Max) and the item count.

### 1.2 Monthly finished-goods stock snapshots, historic

Only two stock snapshots existed: `CURRENT_STOCK_July_2026.csv` (6 July) and `F.G Stock on 1st Aug 2026.xlsx` (5 August). Four weeks apart. This makes it impossible to say whether stock is rising or falling, where cash is accumulating, or whether it is accelerating.

Please export **every FG stock file that exists**, monthly, as far back as they go — ideally April 2025 onward, both PTMT and Plumbing.

For each: `month`, `snapshot_date`, `item_code`, `colour`, `quantity`, `source_filename`. Populate `quantity` directly; do not leave it in `raw_json` only. Note that these files have used at least four different quantity headers (`Qty`, `Closing Stock`, `Qty.`, `Net Stock`) — resolve them into one populated column and record which header each file used.

### 1.3 Item value — weight and/or price per item

`item_weights` had **0 rows**. Every figure in the analysis is therefore in pieces, and nothing can be expressed in rupees. This blocks two of the five rules in the proposed planning method outright (class by value; plan in rupees).

Please provide, per `item_code` (and colour where it varies):

- weight in kg per piece, and/or
- standard cost or factory cost per piece, and/or
- MRP or list price per piece

Any one of these unblocks valuation. All three would be better. If they live outside the app — in an ERP, a price list, or a costing sheet — export from there and say where it came from.

### 1.4 The complete item master, with a component flag

Two separate problems here.

**(a) Missing codes.** 28.7% of PTMT production (3,860,412 pcs over 17 months) sits on codes absent from `item_master`, as does 27.7% of finished-goods stock. 91% of the gap is 25 codes, mostly in the CONNECTION and WASTE PIPE groups — including `324`, `3272`, `323`, `327`, `326`, `342`. These codes are ordered, sold and stocked, but the planner cannot see them.

Please export the **authoritative full item list** — every code the business actually makes or sells — with `item_code`, `colour`, `category`, `segment`, and `is_active`.

**(b) Component vs finished good.** This one is important and is a new finding. Measuring waste as produced-minus-sold gives a spectacular false positive: Ball Cock code `174` shows 173,345 produced against 790 sold, a 219× ratio. It is not waste — those codes are sub-assemblies (*BALL COCK BODY WITHOUT ROD BALL*, *BALL COCK ROD ALUMINIUM*) consumed internally into finished items that sell under different codes. The finished-goods stock file proves it: Ball Cock holds 31,232 pcs, not 897,160.

Please add, per item, either:

- a flag `item_type` ∈ {finished_good, sub_assembly, raw_material}, **or**
- a **bill of materials / parent-child table**: `parent_item_code`, `child_item_code`, `qty_per_parent`

The BOM is much more valuable if it exists. Without one of these, any waste measure built on production against sales will misclassify every intermediate in the range.

### 1.5 Item-code crosswalk between the two sales systems

FY2025-26 sales use a column called `Old Item Code`; FY2026-27 sales use `Item Code`. Only 3,400 codes overlap between the two sets, and total quantities are roughly double in FY26-27 on similar row counts — so the two registers are not directly comparable.

Please export a mapping table: `old_erp_code` → `new_item_code` (→ `item_master.item_code`), covering every code that appears in either register. If no formal mapping exists, say so — that itself explains a lot.

`actuals_daily` holds Plumbing item-level production for only **five months** — Mar, May, Jun, Jul, Aug 2026 — and none of them pair with the same month a year earlier. PTMT has 17 months. Plumbing therefore cannot be analysed at all on a year-on-year basis.

If FY2025-26 machine records exist anywhere — a different endpoint, an archive, the plant's own logs — please export them. If they genuinely do not exist, confirm that so I stop looking.

### 2.3 Pending-order history, with raw headers preserved

Only one pending snapshot was exported. I need the **history** — every pending-order file, monthly, both segments, as far back as they exist.

### 2.4 Buffer multiplier and weekly band history
